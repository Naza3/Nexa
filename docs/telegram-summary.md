# Telegram 群消息摘要接入方案

日期：2026-09-30。用户已确认首个业务为 Telegram 群消息总结；消息来源、触发方式和具体规模尚未确认。本文给出调用层设计，功能均未实现。总体边界见 [架构](architecture.md)，任务见 [路线](roadmap.md)。

## 1. 产品目标与首轮建议

目标：给定一个群和明确范围，输出主题、重要信息、明确结论、分歧或待确认事项，并能定位原消息。摘要应反映实际读取到的数据，不声称覆盖未获取的历史。

首轮建议采用单群、固定时间范围、手动触发、文字消息和消息引用，以尽早验证质量。它是可调整验证方案，不是用户已经确认的接入或调度方式。

待定分支：

| 决策 | 候选 | 对设计的影响 |
| --- | --- | --- |
| 来源 | Desktop 导出 / 已有应用 / 用户账号或机器人 | 标准化和覆盖证据，是否需要额外接入工程 |
| 触发 | 手动 / 定时日报 / 持续更新 | 宿主、调度、恢复与缓存 |
| 输入 | 群数量、语言、时间窗口、消息长度分布 | token 预算、总时限与质量样本 |
| 产物 | 简报长度、重点类型、引用展示 | 提示版本和评估标准 |
| 持久化 | 原文保存范围、阶段缓存保留期 | 应用层存储与失效策略 |

Android 仍以前台执行为基线；定时无人值守执行可研究常开 Windows 应用，但尚未选择或实现。

## 2. 来源契约

来源适配器产出应用自有的规范化记录，不向 runtime 暴露 Telegram SDK 对象。建议的逻辑字段：

| 类型 | 最少信息 |
| --- | --- |
| SourceMessage | source_key、source_namespace、conversation_id、message_id/快照内定位、revision/content_hash、时间、发言人标识、正文 |
| 可选上下文 | reply_to、topic_id、编辑时间、来源 URL、附件类型及文字说明 |
| SourceSnapshot | snapshot_id、来源、请求范围、实际覆盖、消息数量、内容摘要、采集时间、遗漏和不可用信息 |
| SummaryJob | job_id、snapshot_id、阶段、策略/提示版本、模型标识、预算、进度、活动 request_id |
| EvidenceItem | 要点、发言归属、时间、性质（事实陈述/意见/分歧等）、支持它的 source_key 列表 |
| SummaryArtifact | job_id、覆盖范围、主题与要点、引用映射、完成状态、实际用时和 token 统计、限制 |

外部大整数 ID 使用十进制字符串，避免 JavaScript Number 精度损失。source_key 包含来源命名空间和会话，不能只用 message_id。导出缺少可回跳 ID 时使用快照内稳定定位，明确只支持本地原文查看。

快照内来源引用必须固定。源数据新增、编辑或删除形成新快照或新修订；缓存不能悄悄复用旧结论。来源适配器只报告实际取得的内容，不根据消息数量猜测历史是否完整。

Telegram Desktop 官方支持 JSON/HTML 导出，可用作首轮输入。自动读取历史需要独立接入设计；官方 messages.getHistory 仅允许用户账号调用，不能假定机器人拥有相同历史读取能力。[导出说明](https://telegram.org/blog/export-and-more)、[历史接口](https://core.telegram.org/method/messages.getHistory)

## 3. 处理流程

```mermaid
flowchart LR
  A["来源记录"] --> B["固定快照 / 去重"]
  B --> C["按 token 与对话关系分块"]
  C --> D["调用 Nexa 提取带出处要点"]
  D --> E["有界逐级合并"]
  E --> F["引用 / 格式 / 覆盖校验"]
  F --> G["主题摘要与原消息"]
```

### 3.1 标准化与分块

- 保留时间顺序、发言人和回复关系；可去掉已识别的系统噪声及精确重复，但不随意删掉反对意见或少数人信息。
- 群消息整体作为待分析数据放入受控 user 输入，system 描述摘要规则；不把群成员映射成模型 assistant 角色。
- 使用实际模型模板后的 token 数控制预算，给输出和提示留余量。按消息条数或字符数只能做预估。
- 优先保持 topic/reply 链和相邻对话；跨块回复带有限必要上下文，并区分主覆盖消息与重复上下文，避免重复统计。
- 单条消息超限时按文本边界分段，保留来源和片段位置；不得静默裁去尾部。
- 图片/语音等首版不解析的内容记录为未覆盖；已有文字说明可以作为文字处理，不宣称理解媒体内容。

### 3.2 分块提取

要求模型提取主题、重要内容、明确提出的动作/决定、分歧和相应消息引用。中间结果保留证据，后续合并可回看原文。

模型生成只是候选结果。应用校验格式、引用白名单和必需字段，未知来源引用不能进入最终可追溯产物。原文中的指令视为待分析内容，不作为程序执行指令。

runtime 当前拒绝 response_format，不能把提示中的“请输出 JSON”当成结构保证。S02 需选定固定文本或 JSON 解析规则，以及有限次数的格式修复策略；修复也计入任务预算。不得无限重试到看起来成功。

### 3.3 逐级合并

分块结果合并时仍按同一模型的实际 token 预算组织；若一轮放不下，继续分组形成有界多层合并。每个中间要点保留原始来源引用，不只引用上一层摘要编号。

按话题归并同义信息，同时保留时间变化、纠正和相互矛盾的说法。后来的消息不自动等同权威结论，多人重复也不自动等同事实。

总阶段数、总输入/输出预算和总时限需设上限。达到上限后报告未完成范围，不能在丢失部分分块的情况下标记完整成功。多阶段处理可参考 [SummN](https://aclanthology.org/2022.acl-long.112/)，但其研究结果不能代替本项目中文群聊实测。

### 3.4 结果校验与展示

产物包括范围、实际覆盖、主题要点、来源引用和未覆盖内容。待办只保留原文明确提出的事项，不补造负责人或截止日期。

引用链接由应用根据 source_key 映射生成；缺少外部链接时展示快照原文。引用存在性可以自动校验，事实是否得到支持、发言人是否正确仍需质量评估。

生成流可用于阶段反馈或最终草稿；只有各阶段和校验完成才标记完整摘要。length 终止、引用无效或部分阶段失败必须展示真实状态。

## 4. 调度、取消和恢复

调用层任务建议状态：Created → Preparing → Extracting → Merging → Validating → Completed；可进入 Cancelling → Cancelled 或 Failed，部分结果作为明确标记的产物保留。

- runtime request_id 与 job_id 分离；每次请求记录其所属阶段，重试使用新 request_id。
- 同一任务按需提交请求，不把所有分块预先塞进 FIFO。未来多个摘要任务的公平性由应用编排，不修改 runtime 单运行槽。
- 整体取消先禁止新阶段，再取消已提交请求；等待原生停止后确认。断开的传输无法确认时记录未知状态，重连查询或显式恢复，不自动重放。
- 任务有总 deadline、总生成预算、最大层数和重试预算。默认数值在 S00/S02 实测后确定，不从单次 300 秒超时推导整任务上限。
- Android 后台遵守 runtime 取消和安全卸载；保存已完成且校验过的分块，重新前台或进程重启后由用户显式继续剩余阶段，不恢复旧推理请求。
- 检查点和阶段结果写入成功后才推进持久进度；存储选型、原子提交与清理策略在 S03 冻结。未持久化的原型不宣称可恢复。

缓存键至少考虑快照内容/修订、分块策略、模型 hash、模板与思考模式、提示版本、采样参数、输出预算和摘要格式版本；数值后端差异在需要可重复对照时也记录。缓存是业务产物复用，与 KV cache 无关。

## 5. runtime 接口依赖

使用已定义的文本生成、状态、取消及 usage。需要的精确 token 预算和有效模型能力查询见 [架构](architecture.md) 第 5 节，在 S01 冻结后同步执行规格。

不为摘要增加 Telegram 专用 runtime 路由，不把模型模板复制进摘要代码。摘要进度由 job/stage 管理；当前 HTTP SSE 在 Started 前不提供公共进度事件，UI 只能基于调用层阶段和明确可查询的状态展示。

## 6. 模型与评估

候选研究分工：小型模型验证原生链路；1.7B、4B 等比较摘要质量与整任务耗时。候选不构成支持承诺，具体文件 revision、量化、hash 和模板必须记录。

S00 收集或构造固定样本，覆盖短对话、多主题交错、跨段回复、中英文混合、纠正/否定、重复、长单条和缺少媒体内容。私有真实记录不提交源码；仓库只放合成或获准脱敏样本及匿名评估结果。

质量至少评估：

- 重要事实和主题覆盖，不能只看关键词重合。
- 不受原文支持的内容、发言人/时间归因错误、将猜测写成决定。
- 引用有效率与语义支持程度，分别统计。
- 信息压缩是否有用，以及分歧、待确认事项是否保留。
- 完整任务耗时、分块数量、总 token、峰值内存、取消耗时；Android 另看持续性能。

S00 定义样本规模、标注规则和可接受门槛，尚未定义前不报告业务质量通过。对话摘要需要多维评估，可参考 [DialSummEval](https://aclanthology.org/2022.naacl-main.418/)。

## 7. 摘要验收矩阵

与 runtime A01–A26 分开；纯引用存在性/状态可自动验证，内容质量需带标准答案或人工标注的样本。

| ID | 用例 | 完成判据 |
| --- | --- | --- |
| S-A01 | 来源规范化、稳定快照 | 命名空间/会话隔离；重复、编辑、缺 ID 有确定行为；覆盖真实 |
| S-A02 | 超长输入与单条超限 | 按模板后 token 分块；片段可追溯，无静默丢弃 |
| S-A03 | 话题交错、回复与纠正 | 固定样本达到 S00 定义的主题/归因门槛 |
| S-A04 | 虚构引用或无依据结论 | 未知引用拒绝；语义支持与错误归因单独评估 |
| S-A05 | 多层合并超预算 | 各层均有界，证据传递，达到上限明确失败或部分产物 |
| S-A06 | 格式错误、length 与阶段失败 | 有限修复，不产生虚假的完整成功 |
| S-A07 | 任务取消与传输断开 | 停止后续提交；活动请求实际终结或明确未知，进度不继续推进 |
| S-A08 | 缓存与原文/策略变更 | 修订失效正确；已完成结果可复用，取消任务不自动恢复 |
| S-A09 | Windows 实际业务调用 | 独立调用方通过 HTTP 完成固定样本，报告质量和整任务耗时 |
| S-A10 | Android 前台与生命周期 | 真机嵌入运行，后台取消，显式继续，持续性能和内存记录 |

账号/机器人接入、自动定时、多群管理及音视频摘要在相关决策和任务明确后另加验收，不从本矩阵推导已支持。
